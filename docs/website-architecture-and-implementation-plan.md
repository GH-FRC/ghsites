# GHFRC Website Architecture and Implementation Plan

## 1. 文档目的

本文档用于整理 GHFRC 官网的现阶段设想，并补充推荐的技术架构、实施步骤、验收标准、主要风险和开发前待确认事项。

本文档同时记录已进入实施阶段的决策和仍未确定的事项；具体版本的实际范围以相应实施规格和工程日志为准。

需求记录规则：凡用户回答“你来决定”的事项，本文档统一记录为“还不确定”。文档可以在独立章节中提供技术建议，但技术建议不代表 GHFRC 已经确认该决定。

## 2. 项目定位

GHFRC 官网是一支 FRC 队伍的官方网站。网站需要能够展示队伍信息、队伍人数等公开概况、机器人、赛事成果、新闻动态、赞助商及联系方式。当前黑白框架已经支持手机、iPad 和电脑宽度。

网站的长期目标是同时支持英文、简体中文和统一繁体中文。当前版本只生成英文与简体中文；香港、澳门和台湾未来共用一套繁体中文内容与 `/zh-hant/` 路径，目前不生成该路径。

项目的核心目标是把以下三部分相互解耦：

1. 网站框架：决定页面结构、内容区域、尺寸、响应式布局和交互边界。
2. 网站内容：包括各语言的文字、图片、视频及相关元数据。
3. 网站皮肤：决定颜色、字体、装饰、动效和整体视觉风格。

修改任意一层时，应尽量不要求同步修改另外两层。

## 3. 已确认的需求

### 3.1 网站框架

- 第一阶段先用代码制作网站的整体框架。
- 框架需要确定标题、导航、正文、图片、视频、卡片及其他内容区域的位置和尺寸规则。
- 首个框架使用纯黑、纯白和灰阶显示，不加入炫酷视觉效果。
- 框架按照可用宽度切换横向导航与紧凑导航，并支持手机、iPad 和电脑布局。
- 框架代码、皮肤、接口规范和可替换的示例内容统一保存在 GitHub 公开仓库 `ghfrc-website` 中，供任何人查看、复制和修改。
- 公开仓库不包含 GHFRC 的正式文字、图片和视频；真实内容的任何提交历史也不得进入公开仓库。

### 3.2 网站内容

- 正式文字、图片和视频保存在公开仓库之外的独立 GitHub 私有仓库 `ghfrc-website-content` 中。
- 私有内容仓库只向获得授权的 GHFRC 内部人员开放，不设为公开仓库。
- 目前不单独开发可视化后台管理系统。
- 内容通过直接编辑私有仓库中的文件进行管理。
- 一般页面和新闻正文使用 Markdown；导航、队伍公开数据、机器人、赛事和赞助商等结构化资料使用 YAML；图片和视频资料放在独立的媒体目录中。
- 内容层必须与框架层和皮肤层保持独立。
- 私有内容仓库中的正式修改完成后，由系统自动校验、重新构建并发布网站。

### 3.3 网站皮肤

- 视觉效果采用可替换的“皮肤”体系。
- 更换皮肤不得改变正式内容，也不应改变网站的基础信息架构。
- 同一网站可以拥有多款皮肤。
- 网站维护者需要能够决定：
  - 当前默认皮肤；
  - 已安装的皮肤；
  - 允许访客自行切换的皮肤。
- 例如，网站安装了五款皮肤时，可以只向访客开放其中三款。
- 访客可以在本次访问期间切换被允许使用的皮肤。
- 访客再次进入网站时，不恢复上次选择，而是重新使用网站维护者指定的默认皮肤。
- 第一款正式皮肤是默认皮肤，使用 GHFRC 主色 `#911D23`、黑白辅助色和无衬线体。
- 首批正式皮肤至少制作两款，具体总数还未确定。
- 第二款皮肤的方向尚未确定，当前候选参考来自私有内容仓库中的内部粒子风格参考视频；视频中的粒子、实验性动态字体及其他视觉方向都有可能分别制作。
- 第二款皮肤完成并通过验收后，再向访客开放切换。
- 第一阶段的纯黑白框架只用于验证结构，不计入正式皮肤数量。

### 3.4 深色与浅色模式

- 原则上，每款正式皮肤都必须提供浅色和深色两个版本。
- 如果某款特殊皮肤确实不适合双版本，可以经过单独确认后作为例外。
- 网站首次打开时跟随访客设备或浏览器的深色、浅色设置。
- 访客可以在本次访问期间手动切换深色或浅色模式。
- 访客再次进入网站时，不恢复上次手动选择，而是重新跟随系统设置。

### 3.5 多语言行为

- 当前网站只生成简体中文 `/zh-cn/` 与英文 `/en/`。
- 两种语言使用相同的英文 slug，例如 `/zh-cn/frc/` 与 `/en/frc/`。
- 无语言前缀入口首先读取访客长期保存的手动选择；没有有效选择时，读取浏览器的首选语言。
- 任何中文浏览器语言（包括简体、繁体及其地区变体）均进入简体中文；英文和所有其他非中文、空值或无效语言均进入英文。
- 浏览器自动判断结果本身不写入长期保存的手动偏好；没有手动选择时，每次重新进入无前缀入口都会重新判断当前浏览器语言。
- 访客可以手动切换语言，系统会在 `localStorage` 中长期保存选择；下次进入网站时继续使用该语言。
- 直接访问 `/zh-cn/` 或 `/en/` 明确语言 URL 时，URL 始终优先于保存值和浏览器语言，并更新已保存的选择。
- 切换语言时保留当前英文 slug、查询参数和页面片段。
- 未来使用 `/zh-hant/` 为香港、澳门和台湾提供同一套繁体中文；在该内容准备完成前不生成此路径。

### 3.6 品牌基础

- 主色：`#911D23`
- 优先辅助色：纯白与纯黑
- 可选扩展色：从主色推导的深浅色、对比色或反转色，但使用前需要检查可读性和品牌一致性。
- 队徽：正在设计，后续补充。
- 默认皮肤统一使用无衬线体，具体字体尚未确定。
- 其他皮肤可以根据各自的视觉设计单独确定字体，不受默认皮肤字体分类的限制。
- 口号：目前没有。
- 视觉风格：不固定为单一风格，由皮肤系统承载。

### 3.7 域名与发布

- 正式域名确定为 `ghfrc.org`。
- 域名是否由 Squarespace 管理，以及 Squarespace 是否同时用于网站托管，目前还未确定。
- 网站内容修改后由系统自动重新构建并发布。

### 3.8 公开信息、联系方式与访问分析

- 不公开展示现役成员、历届成员、指导老师或导师的个人资料。
- 队伍相关页面只展示队伍人数等适合公开的汇总信息。
- “联系我们”页面不设置访客留言表单，只展示队伍邮箱、微信号及其他官方联系方式。
- 网站需要统计访问量、访客来源和常用页面等数据。
- 可以使用 Cookie 获取较详细的访问数据，但必须向访客显示同意提示。
- 是否直接嵌入视频、社交媒体动态、地图等第三方内容，目前还未确定。

## 4. 推荐的总体架构

### 4.1 已确认的技术栈

正式技术栈确定为：

- Astro：用于生成内容型、多页面、重视加载速度与搜索引擎收录的官网。
- TypeScript：用于定义框架、内容和皮肤之间的稳定接口，并在构建阶段发现格式错误。
- Astro Content Collections：读取独立内容目录中的 Markdown、YAML 或 JSON，并按照预先定义的结构进行校验。
- CSS Custom Properties：把颜色、字体、间距、圆角、阴影和动效参数定义为设计令牌，供不同皮肤替换。
- 少量原生 JavaScript：处理语言、皮肤及深色／浅色模式切换，避免为了简单交互引入过多运行时代码。

推荐 Astro 的主要原因是该网站以内容展示为主，而且要求内容、框架和视觉主题分离。Astro 默认适合生成静态页面，其内容集合可以从本地文件系统或其他来源载入内容，并在构建时进行结构校验。这样既有利于页面性能和搜索引擎收录，也能保留未来改为动态内容源的可能性。

暂不推荐一开始就引入数据库、完整内容管理系统或复杂后端。这些工具会增加维护成本，而现阶段通过 GitHub 私有内容仓库编辑内容已经能够满足需求。

### 4.2 三层分离模型

| 层级 | 负责内容 | 不应负责的内容 |
| --- | --- | --- |
| 框架层 | 页面结构、组件、响应式布局、无障碍规则、内容接口、路由 | GHFRC 的正式内容、具体皮肤风格 |
| 内容层 | 多语言文字、图片、视频、新闻、队伍公开数据、机器人、赛事、赞助商、网站配置 | 页面布局、动画实现、组件内部结构 |
| 皮肤层 | 色彩、字体、背景、边框、圆角、阴影、装饰、动效参数 | 正式文字、图片、页面信息架构 |

三层在构建阶段组合，生成最终可发布的网站。

成就系统属于三层之外的独立运行时模块。它只通过稳定 interface 读取框架提供的区域标记，不保存正式内容，也不读取或修改皮肤。删除成就系统后，框架、内容与皮肤仍可独立组合并正常生成网站。

### 4.3 推荐目录关系

当前仓库结构如下：

```text
ghfrc-website/                    # GitHub 公开仓库
├── achievements/                 # 独立成就规则、进度、通知 UI 与声音
├── framework/                    # 网站框架、组件、测试与黑白基础样式
├── skins/                        # 可替换皮肤与设计令牌
├── content/                      # 可供其他队伍替换的公开示例内容
├── docs/                         # 实施规格与跨模块文档
├── engineering-logs/             # 总工程日志
└── scripts/                      # 内容准备与构建辅助脚本

ghfrc-website-content/            # GitHub 私有内容仓库
├── config/
│   └── locales/
│       ├── zh-CN/                # 完整的简体中文基础内容
│       │   └── site.yaml
│       └── en/                   # 独立的英文覆盖内容
│           └── site.yaml
├── pages/
│   ├── zh-CN/                    # 8 个完整简体中文主要页面
│   └── en/                       # 8 个独立英文覆盖页面
├── robots/                       # 已发布机器人详情资料
├── news/                         # 已发布新闻详情资料
├── media/
│   ├── images/                   # 图片
│   └── videos/                   # 视频或视频引用信息
└── internal-references/          # 仅限内部使用的设计参考资料
```

未来增加统一繁体中文时，在 `config/locales/zh-Hant/` 与 `pages/zh-Hant/` 中建立独立内容文件，并生成 `/zh-hant/` 路径；当前版本不包含这些目录和页面。

构建只在明确设置 `GH_FRC_CONTENT_DIR` 时读取私有内容；如未设置，则读取公开仓库内的 `content/` 示例内容。系统不会因为本地存在同级私有仓库而自动载入真实内容。构建过程只选择一套完整内容来源，不混用不同目录中的文件。

## 5. 三阶段实施方案

### 5.1 第一阶段：建立纯黑白网站框架

#### 目标

在不依赖正式内容和正式皮肤的情况下，完成第一版主要页面、组件、内容区域和响应式布局。

#### 主要工作

1. 建立 Astro 与 TypeScript 项目。
2. 定义全站页面宽度、网格、间距和断点。
3. 建立页头、导航、页脚、标题区、正文区、媒体区、卡片、列表和联系方式等基础组件。
4. 使用纯黑、纯白、灰阶、边框和占位块表达页面层级。
5. 使用虚构占位文字和占位图片测试不同长度的内容。
6. 建立手机、iPad 和电脑端布局规则，并按可用宽度切换导航形式。
7. 定义内容结构与皮肤接口。
8. 建立基础无障碍、键盘操作、性能和页面结构测试。
9. 将框架放入可公开的 GitHub 仓库。

#### 第一阶段应包含的页面

- 首页
- 队伍介绍
- 队伍概况
- 机器人
- 赛事成果
- 新闻动态
- 赞助商
- 联系我们
- 新闻详情页
- 机器人详情页
- 通用错误页面

#### 验收标准

- 未放入 GHFRC 正式内容时，全部页面仍能通过占位内容正常打开。
- 未安装炫酷皮肤时，网站以清晰的纯黑白框架显示。
- 目标手机、iPad 和电脑宽度内没有内容溢出、遮挡或无法操作的问题。
- 替换不同长度的标题、正文和导航文字时，布局仍然稳定。
- 公开仓库及其全部 Git 历史中不存在 GHFRC 的真实内容或内部媒体文件。
- 公开仓库能够独立运行演示版本。

### 5.2 第二阶段：接入独立内容

#### 目标

在不修改页面框架的前提下，通过内部内容文件夹填充和更新正式资料。

#### 主要工作

1. 为页面、新闻、队伍公开数据、机器人、赛事和赞助商建立内容格式。
2. 为各语言建立稳定内容 `id`，按照 ID 合并列表项目，确保翻译关系不受项目顺序影响。
3. 建立图片尺寸、替代文字、版权来源和压缩规则。
4. 建立视频封面、字幕、标题和托管地址规则；允许不同语言覆盖图片或视频，未覆盖时共用简体中文媒体。
5. 在构建前自动检查：
   - 必填字段是否缺失；
   - 英文必需字段是否存在对应内容；
   - 图片或视频引用是否失效；
   - 日期、链接和页面标识是否符合规范。
6. 设计预览流程，使内部人员可以在正式发布前检查修改结果。

#### 已确认的初始内容方式

- 一般页面和新闻正文使用 Markdown。
- 导航、队伍公开数据、机器人、赛事和赞助商等结构化资料使用 YAML。
- 图片保存在内部 `media/images/` 目录。
- 面向访客发布的正式大型视频优先使用独立视频托管服务或对象存储，内容文件夹只保存封面、字幕和引用地址；不建议把大型正式视频直接打包进网站。仅供内部设计使用、不会进入网站构建产物的参考视频可以保存在私有仓库中，并使用 Git LFS 管理。

#### 验收标准

- 修改文字不需要修改框架组件或皮肤文件。
- 替换图片或视频引用不需要修改页面布局代码。
- 内容格式错误会在预览或构建阶段给出明确提示。
- `/zh-cn/` 与 `/en/` 都能正确导航，并使用相同的英文 slug。
- 英文字段或段落缺失时，只回退对应的简体中文内容，不向访客显示待翻译提示。
- 仍有任一必需英文字段缺失时，生成的英文页面自动设置 `noindex`；所有必需英文字段完成后自动恢复可收录状态。
- 翻译检查会报告缺失字段，但不阻断开发、检查或构建。

### 5.3 第三阶段：建立可替换皮肤与动效

#### 目标

让不同视觉风格作为独立皮肤加载，并保证内容和基础框架保持稳定。

#### 皮肤接口建议

每款皮肤至少需要定义：

- 皮肤名称、版本和作者信息；
- 浅色与深色两套设计令牌；特殊皮肤经单独确认后可以例外；
- 主色、辅助色、文字色、背景色和状态色；
- 字体族、字号比例和字重；
- 圆角、边框、阴影和间距表现；
- 背景纹理、图形和装饰素材；
- 动效时长、缓动方式和强度；
- 是否支持减少动态效果；
- 与框架接口的兼容版本。

皮肤原则上只能覆盖设计令牌、装饰资源和经过许可的视觉组件，不应任意修改正文数据或核心页面结构。

#### 访客切换规则

- 网站配置文件指定一款默认皮肤。
- 配置文件列出允许访客选择的皮肤。
- 皮肤选择只在当前访问会话中保留，推荐使用 `sessionStorage`，不使用长期保存。
- 新的访问会话重新加载默认皮肤。
- 深色／浅色模式默认使用 `prefers-color-scheme` 跟随系统。
- 手动选择的深色／浅色模式只影响当前页面；刷新或进入其他页面时重新跟随系统。
- 网站必须支持 `prefers-reduced-motion`，在访客要求减少动态效果时关闭或弱化非必要动画。

#### Figma 与 Pinterest 的确定定位

Figma 与 Pinterest 在设计流程中的分工确定如下：

- Figma：用于建立设计令牌、页面组件、皮肤规范、浅色与深色变体及交互原型；它是设计与交付工具，不是网站运行时必须依赖的插件。
- Pinterest：用于建立不同皮肤的灵感板和情绪板，整理构图、配色、材质、字体及动效方向；它是参考资料来源，不直接接入正式网站代码。
- 从 Pinterest 收集的内容只能作为灵感，不应直接复制受版权保护的图片、插画或完整设计。
- 每款皮肤应先在 Figma 中形成明确规范，再实现为代码，并通过统一的兼容性检查。

#### 验收标准

- 切换皮肤时，页面文字、图片、视频、路由和内容顺序不发生变化。
- 每款皮肤均需支持手机、iPad 和电脑，并兼容当前响应式框架断点。
- 每款皮肤原则上均提供可用的浅色与深色版本；已经单独批准的特殊皮肤可以例外。
- 切换皮肤不会造成页面跳动、文字不可读或组件无法操作。
- 禁用某款皮肤后，访客无法在皮肤选择器中看到或启用它。
- 皮肤选择按上述会话规则处理；深色／浅色的手动选择不保存，浏览器刷新或页面跳转时重新跟随系统。

## 6. 多语言方案

### 6.1 当前语言与路径

当前只生成以下语言：

- 简体中文内容代码：`zh-CN`；页面路径前缀：`/zh-cn/`。
- 英文内容代码与页面路径前缀：`en` 与 `/en/`。

未来统一繁体中文内容代码使用 `zh-Hant`，页面路径使用 `/zh-hant/`。香港、澳门和台湾不拆分为不同内容版本；当前版本不生成该语言的文件或页面。

### 6.2 语言选择优先级

1. 直接访问 `/zh-cn/` 或 `/en/` 明确语言 URL 时，以 URL 为准，并更新长期保存的语言。
2. 访问无语言前缀入口时，优先读取 `localStorage` 中有效的手动选择。
3. 没有有效保存值时，只读取浏览器语言列表中的第一项。
4. 任何中文语言标签，包括简体中文、繁体中文和地区变体，均映射为简体中文。
5. 英文、其他非中文语言、空值及无效语言均映射为英文。

浏览器自动判断结果不会保存为手动偏好。访客手动选择的语言保存在 `localStorage` 中，跨浏览器会话长期生效。切换语言时保留当前页面的英文 slug、查询参数和页面片段。

### 6.3 页面地址

所有语言使用相同的英文 slug：

```text
/en/
/en/frc/
/zh-cn/
/zh-cn/frc/
```

每种语言页面设置对应的 `lang`、`hreflang` 和规范链接。无前缀入口只负责语言判断，不作为独立内容页面。

### 6.4 内容合并与回退

- `config/locales/zh-CN/` 保存完整的简体中文基础内容。
- `config/locales/en/` 保存独立的英文覆盖内容。
- `pages/zh-CN/` 保存 8 个完整简体中文主要页面，`pages/en/` 保存相同英文文件名的独立英文覆盖页面。
- 普通结构化字段缺少英文时，只为该字段回退到简体中文；英文 Markdown 正文为空时，整篇正文回退到简体中文；两种情况均不向访客显示待翻译提示。
- 列表项目使用跨语言稳定 `id` 合并，不依赖数组位置。
- 图片与视频默认共用简体中文引用；英文内容可以覆盖媒体字段以使用不同素材。

### 6.5 翻译完整性与搜索引擎收录

- `npm run check:translations` 为维护者列出缺少的英文字段，但返回成功，不阻断开发、检查或构建。
- 只要仍有任一必需英文字段缺失，生成的英文页面就自动加入 `noindex`。
- 所有必需英文字段完成后，英文页面自动恢复可收录状态，无需手动修改搜索引擎配置。

## 8. 推荐的工作流程

### 8.1 框架修改

1. 在公开仓库的 `framework/` 中修改组件或布局。
2. 使用占位内容运行自动测试。
3. 使用内部内容目录进行本地预览。
4. 确认全部皮肤兼容后发布框架更新。

### 8.2 内容修改

1. 内部人员在 GitHub 私有内容仓库中编辑并提交内容。
2. 系统自动校验格式、稳定内容 ID、英文翻译完整性和媒体引用；缺失翻译只报告，不阻断构建。
3. 系统生成受限访问的预览版本，供内部检查。
4. 正式内容合并到指定发布分支后，系统自动构建并发布网站。

### 8.3 皮肤修改

1. 在 Pinterest 中建立灵感板。
2. 在 Figma 中建立设计令牌、组件状态及浅色／深色变体。
3. 按统一皮肤接口实现代码。
4. 使用同一套占位内容和正式内容进行兼容性测试。
5. 在网站配置中决定默认皮肤及允许访客选择的皮肤。

## 9. 主要风险与应对方案

### 9.1 “绝对不会影响”无法只靠文件夹分开实现

框架、内容和皮肤可以高度解耦，但不能仅凭目录结构保证任何修改都绝对没有影响。例如，极长标题仍可能影响布局，低对比度皮肤仍可能影响阅读。

应对方案：定义严格接口、内容长度规则、设计令牌、自动校验、视觉回归测试和多设备验收标准。

### 9.2 GitHub 私有仓库不等于已发布内容对访客保密

内部源文件保存在 GitHub 私有仓库中，但正式网站公开展示的文字和媒体仍会被发送到访客浏览器，因此访客可能查看或下载这些已发布内容。

应对方案：只发布允许公开的资料；不要在内容目录中加入个人隐私、密钥、内部文件或未获授权的媒体。

### 9.3 GitHub 私有内容仓库会增加构建与部署复杂度

托管平台在构建网站时必须能够读取内部内容。若平台只能访问公开仓库，网站将无法自动获得正式内容。

应对方案：使用有权读取私有仓库的自动构建流程，在构建时组合公开框架与私有内容；限制自动化凭证权限，保护密钥，并确保构建日志不会泄露内部文件。

### 9.4 大型视频会影响性能和部署

大型视频会显著增加构建时间、存储占用和访问流量，部分静态托管平台还限制单个文件大小。

应对方案：优先使用专业视频托管服务或对象存储，并提供压缩封面、字幕和延迟加载。

### 9.5 皮肤可能破坏可读性与性能

复杂背景、低对比度配色、过多字体和动画可能造成阅读困难、加载缓慢或设备发热。

应对方案：每款皮肤必须通过文字对比度、键盘操作、减少动态效果、移动端性能和图片体积检查。

### 9.6 多语言内容可能不同步

新增页面或新闻后，英文内容可能缺失、过期或链接到错误页面。

应对方案：使用稳定内容 ID 与构建前翻译报告；字段或段落缺失时只回退对应简体中文内容，并在仍有任一必需英文字段缺失时为生成的英文页面自动加入 `noindex`。访客不显示待翻译提示，所有必需英文字段完成后自动恢复可收录状态。

### 9.7 Squarespace 的角色尚未确定

Squarespace 可以管理域名并通过 DNS 指向其他托管平台，但其自定义代码能力存在平台边界。当前所设想的独立 Astro 项目、外部内容目录和可插拔皮肤，更适合先生成完整网站，再部署到支持静态站点的平台。

建议方向：优先考虑只在 Squarespace 购买和管理域名，把网站部署到独立静态托管平台；最终决定留到正式开发开始前确认。

## 10. 托管与发布的初步建议

### 10.1 当前推荐方向

- 域名：可以在 Squarespace 购买和管理。
- 网站：优先生成静态网站并部署到独立静态托管平台。
- 内容：保存在 GitHub 私有仓库中，通过受控的自动构建流程加入最终网站。
- 首选候选平台：Cloudflare Pages。
- 备选平台：Vercel。

选择独立静态托管的原因是，它更适合完整控制 Astro 项目、皮肤系统、自动构建、预览和自定义域名。Squarespace 官方资料也说明，其域名具有 DNS 控制能力，可以指向其他网站。

### 10.2 费用说明

- 免费方案：Cloudflare 的开发者平台免费方案当前为每月 `US$0`，包含静态资源托管，但存在请求量、构建次数、文件数量和单文件大小等限制。
- Cloudflare 付费方案：Workers Paid 当前按月计费，起价为每月 `US$5`，包含一定用量，超出部分按使用量计费。只有在动态功能或资源用量超过免费层时才需要考虑。
- Vercel 免费方案：Hobby 当前为每月 `US$0`，主要面向个人及非商业项目；GHFRC 官网使用前需要核对是否符合该方案范围。
- Vercel 付费方案：Pro 当前按月计费，平台费为每月 `US$20`，包含一个可部署成员席位和每月 `US$20` 的用量额度；超出额度后按使用量计费。
- 以上价格于 2026 年 8 月 9 日根据官方价格页核对，正式购买前仍需再次确认。
- Squarespace 域名注册费与网站订阅费不是同一项费用，正式购买前需要分别确认。

## 11. 开始开发前待确认事项

以下内容尚未由 GHFRC 最终决定，不应被视为已确认需求：

1. Squarespace 只负责域名管理，还是同时负责网站托管。
2. 最终队徽文件、队徽使用规范和安全留白。
3. 默认皮肤使用的具体无衬线字体及其授权方式；字体分类已经确定。
4. 正式皮肤的最终数量；目前只确定至少两款。
5. 第二款及后续皮肤的名称和最终视觉方向；私有内部参考视频中的多种风格目前均为候选。
6. 具体访问分析工具、Cookie 保存期限、数据保留周期和隐私政策文本。
7. 是否直接嵌入视频、社交媒体动态、地图等第三方内容。
8. 图片、视频、音乐版权和未成年队员肖像授权的审核规则；目前尚未建立。
9. 视频最终使用的托管平台或对象存储服务。
10. 机器人页面是否公开 CAD、代码、详细技术参数及设计过程。
11. 内容编辑、多语言翻译、审核和正式发布分别由谁负责。
12. GitHub 私有内容仓库的具体访问权限、分支保护和额外备份规则。
13. “联系我们”页面最终展示的队伍邮箱、微信号和其他官方账号。

这些事项应在各自影响到开发时逐项确认，不需要在当前阶段一次性决定完毕。

- 不在本总体规划文档中定义当前具体开发版本之外的实现细节；当前实施范围以版本规格和工程日志为准。
- 不制作正式皮肤或动画。

## 13. 推荐结论

GHFRC 官网采用“GitHub 公开网站仓库 + GitHub 私有真实内容仓库 + 自动构建发布流程”的架构。公开仓库同时保存框架、皮肤、独立成就系统和可替换的示例内容，使外界能够把项目直接作为模板使用；私有仓库只保存 GHFRC 真实内容和内部参考资料。第一阶段先完成公开的响应式纯黑白框架；第二阶段用经过校验的私有内容填充多语言网站；第三阶段通过设计令牌和稳定接口加入可替换皮肤。
正式技术栈采用 Astro、TypeScript、Astro Content Collections 和 CSS Custom Properties，并通过自动化流程完成内容检查、网站构建与发布。该方案能够以较低复杂度实现现阶段目标，同时为未来增加远程内容源或内容管理系统保留扩展空间。
